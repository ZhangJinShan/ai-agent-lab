# 用户中心故障处理手册

> 面向:一线值班同学 | 最后更新:2026-09-20
> 升级路径:一线 → 平台组 oncall(企业微信「平台组-oncall」群)→ 架构组(电话)
> 处理原则:**先止血(止损优先于定位),再排查**;所有操作记录到工单,禁止直接改生产数据,禁止跳过验证步骤提前收工。

## 故障等级定义

| 等级 | 定义 | 响应要求 | 升级时限 |
|---|---|---|---|
| P0 | 登录/鉴权全量不可用,或资损风险 | 5 分钟内响应,全员投入 | 10 分钟未止血升级架构组 |
| P1 | 核心接口错误率 > 10%,或大面积变慢 | 10 分钟内响应 | 30 分钟未止血升级架构组 |
| P2 | 非核心功能异常,有替代方案 | 30 分钟内响应 | 2 小时未恢复升级平台组 |
| P3 | 体验问题,不影响主流程 | 当日处理 | 无 |

## 登录大面积失败(网关 500)

**现象**:监控告警「登录成功率 < 50%」,用户反馈输对密码也登不进;网关日志大量 `POST /api/v1/users/login` 返回 500,错误栈指向 `JedisConnectionException`。故障等级:P0。

**常见原因**:Redis 连接池打满。登录依赖 Redis 缓存权限点和做密码错误计数,连接池默认 50;当有异常流量(如爬虫撞库)或连接未释放的发布事故时,池子会被耗尽,后续请求全部拿不到连接,报获取连接超时。

**处理步骤**:

1. 确认影响面:看 Grafana「登录成功率」面板和网关 QPS,判断是全量还是部分机器;若是部分机器,先把问题机器摘流。
2. 止血:如果是刚发布引起,先回滚上一个版本;如果是流量异常,在网关层对 `/api/v1/users/login` 按 IP 限流(临时收紧到 20 次/分钟)。
3. 扩容连接池:调整配置 `redis.pool.max-active`(参考配置说明文档),先推一台观察 5 分钟再全量推。
4. 验证恢复:登录成功率回到 99% 以上,连续观察 15 分钟,确认没有反复。
5. 复盘:输出故障报告,重点写清楚「连接池耗尽的诱因」和「为什么没有更早告警」,行动项落到人和日期。

## 接口响应缓慢(p99 飙升)

**现象**:告警「用户信息查询 p99 > 2s」(正常在 50ms 内),但错误率没有明显上升;用户反馈页面加载慢,刷新后偶尔正常。故障等级:P1。

**常见原因**:MySQL 主从延迟。用户信息查询走读库,当大促导数据或批量任务压到主库时,从库回放延迟变大,查询全部变慢。次要原因:慢 SQL(未走索引的模糊查询)、GC 停顿、宿主机 CPU 被邻居打满。

**处理步骤**:

1. 先看数据库监控的「主从延迟」指标;延迟 > 1s 基本可定位为本原因。
2. 若是批量任务引起:暂停批量任务,延迟通常在几分钟内回落。
3. 若延迟不回落:检查从库机器负载和备份任务,必要时切流到备用从库。
4. 若主从延迟正常:打开慢 SQL 日志,定位未走索引的查询;临时手段是限流该接口或加索引(加索引需 DBA 评估锁表风险)。
5. 若以上都正常:看应用 GC 日志和宿主机 CPU,top 命令确认是否被邻居进程打满,是则申请迁移宿主机。
6. 验证恢复:p99 回落到 100ms 以内,连续观察 15 分钟。
7. 复盘:评估读写分离的兜底策略(主库降级开关)。

## 短信验证码收不到

**现象**:客服反馈多位用户收不到登录/改密码的短信;短信平台控制台显示「发送成功」但用户手机无记录。故障等级:P2(有语音验证码替代)。

**常见原因**:第三方短信通道积压或被运营商风控拦截。单日发送量突增(如营销活动)会触发运营商的频控策略,消息进入延迟队列,表现为「发了但收不到」。

**处理步骤**:

1. 登录短信平台控制台,查看「发送状态」分布:如果大量「发送中」而非「成功」,是通道积压。
2. 切换备用短信通道(平台控制台 → 通道管理 → 启用备用通道)。
3. 如果是运营商风控:联系供应商报备签名和模板,申请解除频控。
4. 期间引导用户使用「语音验证码」作为替代方案,客服话术见工单模板库。
5. 验证恢复:新发送的短信 30 秒内到达,连续观察 15 分钟。
6. 复盘:补充短信通道的多活配置和发送量分级告警。

## 缓存穿透导致数据库告警

**现象**:数据库 QPS 告警突增,但业务 QPS 平稳;慢日志里出现大量同一个不存在 userId 的查询;Redis 命中率监控跌破 50%。故障等级:P1。

**常见原因**:恶意或爬虫用不存在的 userId 高频刷「用户信息查询接口」。缓存查不到就打到数据库,而不存在的数据永远不会被缓存,形成穿透;当无效 ID 是随机生成时,缓存彻底失效。

**处理步骤**:

1. 从慢日志/网关访问日志找出高频无效 userId 和来源 IP。
2. 止血:网关对该 IP 段限流;对 `GET /api/v1/users/{userId}` 增加「空值缓存」——查不到的 userId 缓存空结果 60 秒,挡住重复穿透。
3. 观察数据库 QPS 回落,确认缓存命中率恢复到 95% 以上。
4. 复盘:把「空值缓存」固化到代码里(当前是临时脚本),评估布隆过滤器方案。

## 磁盘水位告警(日志盘打满)

**现象**:告警「磁盘使用率 > 85%」,应用日志目录所在盘接近满;应用开始报写日志异常,严重时进程被 OOM Killer 杀掉。故障等级:P1。

**常见原因**:有同学排查问题时把日志级别临时调成 DEBUG 后忘记调回,日志量放大约 8 倍;或日志清理任务被误关。

**处理步骤**:

1. 确认日志级别:检查配置中心 `log.level`,如果是 DEBUG 且非排查窗口,立即改回 INFO(热生效,无需重启)。
2. 确认清理任务:`log.retention-days` 默认 15 天,检查清理脚本 cron 是否在跑。
3. 应急清理:删除 3 天前的归档日志(`*.log.*.gz`),**不要删除正在写入的日志文件**。
4. 验证恢复:磁盘水位回落到 70% 以下,应用写日志正常。
5. 复盘:增加日志级别变更的审批和自动回滚(改 DEBUG 超过 1 小时自动回 INFO)。

## 通用排查工具与常用信息

- **监控面板**:Grafana「用户中心」大屏(登录成功率 / 接口 p99 / QPS / 错误率);Redis、MySQL 实例监控在「中间件」大屏。
- **日志查看**:机器上的 `/data/logs/user-center/` 目录;按 `X-Request-Id` 可以在链路追踪系统里串起一次请求的全部日志。
- **发布平台**:发布与回滚走「流云」发布平台,回滚按钮在版本历史页,回滚后无需重启网关。
- **工单模板**:故障报告模板、客服话术模板在知识库「用户中心 / 运维」目录下。
